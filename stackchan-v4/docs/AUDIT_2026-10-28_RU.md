## 3. Подтверждённые ошибки и риски

### A01 — P1: парсер обученных весов читает за пределами файла

**Место:** `main/v4/learned_blob.h:37–47,66–71`; `main/net/learned_store.cpp:148–167`.

`valid()` проверяет magic, общую длину и CRC, но не проверяет, помещается ли таблица `Header.count` записей в файл. `View::find()` затем обходит таблицу без границ. Проверка `offset + count * 4u > total` дополнительно допускает переполнение `uint32_t`.

**Воспроизведено:** заголовок длиной 32 байта с `count=1`, `total=32`, корректным CRC пустого тела проходит `valid()`. Вызов `find("zones.shift",13)` даёт AddressSanitizer `heap-buffer-overflow` на строке 43. Второй файл длиной 80 байт, с записью `zones.shift`, `count=13`, `offset=0xfffffff0`, также проходит проверку и возвращает недопустимый указатель.

**Последствие:** повреждённый либо специально сформированный blob может вызвать чтение произвольного адреса и падение. CRC удостоверяет целостность байтов, но не корректность структуры. OTA-обработчик требует токен; наличие этой авторизации не устраняет ошибку формата.

**Исправить:** единый валидатор на ПК и устройстве; `count <= (total-sizeof(Header))/sizeof(Entry)`; проверка диапазонов через вычитание, без переполняющегося сложения; запрет пересечения данных с таблицей; проверка выравнивания, типов, размеров, дубликатов, конечности чисел и совместимости. `View` должен хранить доступную длину. Добавить ASan/UBSan-тесты усечённых файлов и фаззинг формата.

### A02 — P1: неподтверждённый UDP-пакет меняет адрес получателя OTA-токена

**Место:** `tools/robot/lifelogd.py:108–124`; `tools/robot/ota.py:36–48`.

Получатель дневника слушает `0.0.0.0`. Пакет с подходящим magic/header меняет `robot.json` на IP отправителя до проверки содержимого. `ota.py` доверяет этому адресу и отправляет туда `X-Token` по HTTP.

**Воспроизведено без сетевого трафика:** подставной сокет и временный каталог; пакет от тестового адреса `192.0.2.123` записал этот адрес в `robot.json`.

**Последствие:** узел, который может доставить UDP-пакет при действующих сетевых правилах, способен подменить адрес устройства; последующий запрос администратора или ночного сервиса отправит ему токен. Это локальная сетевая поверхность атаки, не доказательство доступности из интернета.

**Исправить:** закреплённая идентичность устройства; отдельный ключ аутентификации дневника/HMAC и защита от повторов; проверка источника до изменения адреса; атомарная запись JSON. Не использовать секрет OTA как доказательство доверия неизвестному адресу. Защитить канал управления TLS с проверкой устройства либо эквивалентным аутентифицированным протоколом. Токен не публиковался и его значение в отчёт не включено.

### A03 — P1: короткий пакет завершает процесс дневника

**Место:** `tools/robot/lifelogd.py:140–143`; `tools/v4/diary.py:86–114`.

Проверяется только наличие 16-байтового общего заголовка. Для строки `kind=2` сразу читаются ещё 4 байта. Для тиков офлайн-читатель доверяет количеству записей и размеру строки.

**Воспроизведено:** пакет из одного заголовка `SCL1`, `kind=2` вызывает необработанный `struct.error`: требуется 20 байт, доступно 16. До падения пакет уже записывается в дневник. Перезапуск systemd не делает сохранённый пакет корректным для последующего анализа.

**Исправить:** проверять полный ожидаемый размер для каждого kind, число тиков и схему; отбрасывать повреждённые записи со счётчиком; офлайн-читатель должен уметь пропустить/карантинировать плохую запись и продолжить. Добавить тесты на пустые, короткие, неизвестные и чрезмерные сообщения.

### A04 — P1: «здоровая минута» OTA означает только прошедшую минуту

**Место:** `main/robot_runtime.cpp:begin(), confirmFirmware()`; около строк 567–576.

Ошибки старта IMU, микрофона, камеры, движения и других подсистем логируются, но `begin()` в итоге возвращает `true`. `confirmFirmware()` после 60 секунд подтверждает прошивку без оценки сенсоров, нейросетей, ошибок или прогресса задач; результат `esp_ota_mark_app_valid_cancel_rollback()` не проверяется.

**По коду:** работающее главное кольцо с неработающими чувствами может подтвердить обновление. Отказ периферии после подтверждения уже не вызывает автоматический bootloader rollback.

**Исправить:** явные обязательные критерии здоровья и допустимого ухудшения: успешные решения мозга, свежие данные обязательных сенсоров, отсутствие критических ошибок и нормальное питание. Подтверждать только после выполнения критериев и успешного ответа ESP-IDF. Требования диагностики перед подтверждением описаны в [официальной документации ESP-IDF 5.5.4](https://docs.espressif.com/projects/esp-idf/en/v5.5.4/esp32s3/api-reference/system/ota.html).

### A05 — P1: переключение learned-слотов не оформлено как атомарная транзакция

**Место:** `main/net/learned_store.cpp:90–111,114–167`; `main/net/learned_store.h:25–49`; `main/robot_runtime.cpp:superviseLearned()`.

HTTP-задача пишет blob, главное кольцо его переключает. Только флаг `switch_` атомарный; `slot_`, `trial_` и связанные состояния разделяются без общей синхронизации. Между `finishWrite()/requestSwitch()` и обработкой запроса ещё нет запрета следующей загрузки: `beginWrite()` проверяет только `trial_`. Получается окно, в котором следующая запись может попасть в слот, который главное кольцо уже начинает отображать/читать. Это установленный риск конкурентного выполнения; на реальном ESP32 он не воспроизводился.

`confirm()` выставляет `trial_=false` ещё до открытия NVS; ошибки `nvs_set_*`/`nvs_commit` большей частью не обрабатываются. В `open()` невалидный пробный blob может оставить `trial_` установленным; при штатной работе врождённой сети такой слот впоследствии может быть подтверждён.

**Исправить:** состояния `idle → writing → validated → pending → trial → confirmed/reverted`, запрет новой записи с момента начала транзакции, один владелец состояния или mutex/очередь команд. Фиксировать состояние в RAM только после успешного NVS commit. Проверять все ошибки; откатывать невалидный кандидат сразу. Протестировать две последовательные загрузки, обрыв, выключение питания и ошибки NVS на каждом шаге.

### A06 — P1: без синхронизации часов ночная тишина заканчивается через две минуты

**Место:** `main/core/brain_loop.cpp:231`.

При неизвестном времени `night_ = now < 120000`. Если ночью перезапустить устройство без Wi-Fi/NTP, через две минуты применяются дневные правила.

**Исправить:** отдельное состояние «время неизвестно» с тихим режимом; восстановление времени из доступного надёжного источника; явная пользовательская возможность включить дневной режим. Проверить ночную загрузку без сети, длительную недоступность NTP, восстановление времени и переход суток. Текущий `night_quiet` этого отказа не моделирует.

### A07 — P1: устаревшие показания продолжают считаться исправными

**Место:** `main/sensors/presence_engine.h:25–26`, `presence_engine.cpp:update()`; `main/core/brain_loop.cpp:164–191`; `main/sensors/imu_engine.cpp`.

`proximityOk()` означает «когда-то установлен baseline», а `lightOk()` — «когда-то был световой замер». После ошибки I²C последние значения и эти флаги остаются. Аналогично `r.imuOk` зависит от накопленного количества отсчётов, а не от свежести успешного чтения IMU; при отсутствии IMU нулевые данные всё равно попадают в накопитель.

**Последствие:** застывший датчик может изображать постоянного человека рядом или нормальное положение тела; поведение и обучение используют ложную уверенность.

**Исправить:** у каждого сигнала хранить время последнего успешного чтения, возраст, валидность и причину отказа. Передавать эти признаки в журнал и обработку состояния. Пропажа данных должна давать неопределённость, а не «всё спокойно». Для критической обратной связи движения предусмотреть безопасное ограничение моторики.

### A08 — P1: нормальный речевой ответ на реплику не получает награду

**Место:** `tools/v4/reward_v4.py:43–48`; `main/core/brain_loop.cpp:hear()`; `main/core/brain_loop.h:kOwnVoiceTailMs`.

После каждого `said` ночной reward исключает речь в течение 5 секунд. В прошивке уже есть VoiceCheck и отдельная маска 1,5 секунды после активного собственного голоса. Таким образом, даже дошедшая через текущий слух настоящая речь может быть отброшена ещё раз. Для социальной причинности ожидается ответ примерно в окне 0,5–4 секунды.

**Воспроизведено:** искусственная последовательность с чистой речью длительностью 2 секунды: начало через 1 секунду после `said` даёт `talk_rewards=0`; через 6 секунд — `talk_rewards=1`.

**Исправить:** единый источник событий «внешняя речь», журнал начала/конца собственного звука и его подавления; общие правила для онлайн-причинности и ночного reward. Проверять ответы человека на нескольких задержках, эхо, сервошум, телевизор и речь одновременно с движением. Простое снятие всех масок вернёт обучение на собственном шуме.

### A09 — P1: конец записи и разрывы могут превращаться в отрицательный опыт

**Место:** `tools/v4/reward_v4.py:55–60`; `tools/v4/sleep_v4.py:81–112,115–122`.

`left_alone` смотрит вперёд на минуту, но не требует наличия полной наблюдаемой минуты. Последний вызов в записи считается неотвеченным, даже если запись просто закончилась. Reward вычисляется на всём дне до разделения по boot; свёртки используют индексы как равномерные тики, не учитывая потери UDP, паузы и перезагрузки. `load_life()` считает `gaps`, но не использует их как запрет обучения. Boot, пересёкший полночь, также разделяется загрузкой по дням.

**Воспроизведено:** контакт перед концом записи и `said` в последнем тике дают `left_alone=1`, хотя будущего наблюдения нет.

**Исправить:** непрерывные эпизоды по boot, seq и реальному времени; окна в миллисекундах; неизвестный исход для хвоста записи и пропусков. Не переносить награду через границу эпизода. Различать отсутствие ответа и отсутствие наблюдения.

### A10 — P1: обучение действует в другом мире исполнения

**Место:** `tools/v4/train_nn_v4.py:label()`; `tools/v4/teacher_nn.py:apply()`; `tools/v4/sleep_v4.py:taken()`; `main/v4/brain_v4.cpp:executed()`; `main/v4/v4_executor.cpp`.

Учитель обновляет память по условному исполнению выходов сети. Настоящий исполнитель использует бюджет звука, пороги/перевооружение голоса, выдержку лица, фронт режима жеста, паузы, самостоятельные взгляды и ориентировочный рефлекс. `taken()` берёт argmax/порог из `nn_*`, а не фактически принятые и завершённые действия. Это не обязательно делает любое обучение намерений неправильным, но текущий контракт не описывает и не учитывает разницу.

DAgger в `label()` использует заранее посчитанные SNN-последовательности и Python AnswerWorld, а не настоящий C++ исполнитель и сенсомоторную среду. Ответы дополнительно внедряются в выходы SNN через `contingency.inject`; Muse рассчитывается до этих внедрений. Поэтому это ограниченный вариант DAgger, а не полный rollout устройства.

Незакоммиченное исправление `BrainV4::executed()` согласует координаты головы с учителем, но для этого перестаёт использовать `e.headYawDeg/e.headPitchDeg` и ведёт внутреннюю модель выбранного взгляда. Это полезное исправление несовместимости входов, однако не заменяет обратную связь реального положения.

**Переделать:** единый контракт `intent / accepted / started / completed / cancelled`, с `action_id`, причиной подавления и параметрами; различать желаемую, командную и наблюдаемую позу. Учителя и rollout должны использовать ту же семантику исполнения. Проверять и обучать на состояниях, достижимых с реальными бюджетами и задержками.

### A11 — P1: головы действий практически не проходят ночное обучение

**Место:** `tools/v4/sleep_v4.py:train_heads(), change(), main()`; доступный `data/life/sleep_v4.log`.

По доступным записям попытки AWR были отклонены: 25.10 KL=0,0576; 26.10=0,3597; проба 27.10=0,0620; ночь 28.10=0,0599 при пороге 0,05. Ночь 27.10 не набрала минимального дневного объёма для голов. При этом сдвиги зон и смещения Muse могли успешно отправляться. Поэтому успешное сообщение о новом blob не доказывает, что робот выучил новые действия.

**Новый dry-run в аудите:** дни 27–28.10, 11 фрагментов boot, 809 552 решения, 14,4 часа дневных решений, 388 событий награды; KL=0,0608, изменилось 2,3% выборов — головы снова отклонены. Кандидат без новых голов дополнительно не прошёл поведенческий gate. Отправки не было; артефакты этой пробы перенаправлены в `/tmp`.

**Исправить:** сохранять лучший допустимый промежуточный checkpoint, уменьшать шаг/число эпох, делать раннюю остановку по ограничению и проверку на отдельном эпизодном наборе. Измерять улучшение ответа человека или выбранной метрики относительно текущей политики. Не ослаблять порог KL только ради факта обновления. Ночной отчёт должен явно различать обновления голов, зон и Muse.

**Параллельная работа после снимка:** другой агент уже изменяет `sleep_v4.py`: новую функцию обучения и частичный шаг через `blend`. Вывод A11 описывает проверенную прежнюю реализацию и реальные ночные отчёты. Новый алгоритм этим аудитом не валидирован; его нельзя ни считать проверенным исправлением, ни оценивать по полученному здесь старому KL.

### A12 — P1: replay-gate слишком слаб и не удостоверяет происхождение данных

**Место:** `tools/v4/sleep_v4.py:load_life(), replay(), main()`; `main/net/life_log.h`; `tools/v4/learned.py:nn_id()`.

Replay проверяется медианой максимальной ошибки эмоций по тикам. Медиана может пропустить почти половину ошибочных решений. Количество разрывов не участвует в gate; нет обязательного идентификатора прошивки/схемы входов/весов для каждого эпизода. Fingerprint learned-голов полезен, но относится к GRU и emotion head, а не ко всей семантике сенсоров, исполнителя и дневника.

**Воспроизведено:** в 49 из 100 строк подменены логируемые вероятности эмоций; `replay()` вернул медианную ошибку `0.0`.

**Исправить:** манифест запуска с hash прошивки, моделей, схемы и настроек; сегментация по непрерывности; прогрев GRU для фрагментов; p95/p99/max и доля несовпадающих решений дополнительно к медиане. Проверять действия и семантику записи. Зоны и Muse сейчас меняются независимо от того, прошли ли эпизоды replay-gate: это тоже должно иметь явные собственные критерии качества.

### A13 — P1: голова остаётся главным ограничением физической надёжности

**Место:** `main/motion/motion_engine.cpp`, `main/robot_runtime.cpp:superviseServos()`, `docs/HARDWARE.md`, `tools/v4/jerks.py`.

На этой плате отсутствует надёжная обратная связь SCS. `getCurrentDeg()` возвращает модель команды, а не измеренную позу. Предположение «сервопривод пришёл в точку» нарушается при зависании, потере пакета и смещении обесточенной головы. Ограничение скорости программной траектории само по себе не ограничивает физический рывок рассогласованного привода.

**Проверка текущего доступного дневника 28.10:** 2 окна с рывками, 10 зависаний, 186 включений питания серв; 1,1% и 5,4% относительно включений. Данные доступны примерно до 07:00, это не полный день. Детектор окон и отдельные сообщения у включения считают события по-разному: в часе 06 зарегистрировано 3 сообщения о рывках, но 2 окна по критериям `jerks.py`.

Причины из журнала — пропущенная установка position mode, рассогласование положения, питание — имеют разную степень подтверждения. Не считать одну из них окончательно доказанной для всех оставшихся случаев без измерения пакетов и питания. Текущий детектор пика в первую очередь логирует рывок; это не аварийное ограничение скорости.

**Следующая работа:** воспроизводимый стенд с журналом UART и измерением питания при включении; отдельно режим серв, потеря пакетов, механическая нагрузка и положение после выключения. Нужны наблюдаемая/оценённая поза с уверенностью, ограничение повторных восстановлений и состояние отказа. При невозможности надёжной обратной связи оценить ремонт интерфейса или замену привода/платы. Нельзя компенсировать неисправную механику только обучением эмоций.

### A14 — P2: бюджет тела зависит от нарисованного лица

**Место:** `main/core/brain_loop.cpp:271`; `main/v4/body_v4.cpp`; `main/v4/channel_encoder.cpp:105–108`.

`asleep` означает «ночной режим ИЛИ показано Sleepy». При таком лице бюджет восстанавливается, даже если исполнитель продолжает дневную активность. Показатель телесного состояния получает обратную связь от визуального представления. Кроме того, батарея и социально-стрессовый бюджет объединены через `max` в один канал hunger: сеть не может отличить причины одинакового значения.

**Переделать:** отдельное состояние отдыха с условиями входа, минимальной длительностью, ограничением моторики/звука и фактическим расходом. Лицо должно выражать это состояние. Развести электрический заряд, нагрузку/восстановление и социальную потребность; их сочетание может влиять на общий affect, но причины должны оставаться различимыми.

### A15 — P2: непрерывность «жизни» теряется при перезагрузке

**Место:** `main/v4/body_v4.h`, `body_v4.cpp:step()`; `main/v4/brain_v4.h`; `main/v4/contingency_v4.h`; `docs/CONTINGENCY.md`.

После boot бюджет начинается с 0,85, давление сна — с обычной кривой часа; текущая причинность, кратковременный контекст и состояние Muse сбрасываются. На устройстве нет реализованной долговременной эпизодической памяти или устойчивой модели конкретного человека. «Жизненная» причинность в концепте остаётся будущим шагом. Полный дневник находится на ПК, но сам по себе не является доступной роботу памятью.

**Улучшить:** небольшой версионированный снимок медленных состояний с ограниченной частотой записи, обработкой времени выключения и повреждения. Сохранять устойчивые предпочтения и несколько значимых эпизодов с причиной/исходом. Не пытаться сохранять каждый тик во flash. Прежде чем вводить новые состояния, определить, как каждое изменит наблюдаемое поведение.

### A16 — P2: Muse создаёт вариативность, но заявленная обучаемая творческая система реализована частично

**Место:** `main/v4/muse_v4.cpp`; `tools/v4/muse.py`; `tools/v4/sleep_v4.py:surprise_of(), learn_muse()`; `docs/CREATIVITY.md`.

Резервуар и readout фиксированы. Ночь меняет смещения `muse.bias`, а не обучает readout методом AWR, как утверждают некоторые разделы документа. Пять «идей» имеют заранее заданные трактовки учителем. Habituation ослабляет положительный выход, но прямо не возвращается в состояние резервуара, поэтому фраза о выталкивании его в новые области сильнее реализации.

Curiosity — ошибка ridge-прогноза каналов через секунду, обученного на том же дне. Это не измерение прогресса обучения и не модель результата собственного действия: действие отсутствует среди входов предиктора. Шумная среда может давать высокую ошибку без полезного открытия.

**Улучшить:** честно назвать текущий механизм генератором структурированных инициатив. Для развития использовать прогноз с собственным действием и контекстом; оценивать улучшение на отложенных эпизодах, отдельно от непрогнозируемого шума. Learning progress — именно цель подхода [Oudeyer, Kaplan, Hafner, 2007](https://www.pyoudeyer.com/ims.pdf). Не принимать спектральный радиус около единицы за самостоятельное доказательство творческой способности.

### A17 — P2: статистическая контингентность ещё не доказывает причинность

**Место:** `main/v4/contingency_v4.cpp:step(), finish()`; `tools/v4/behavior_test_v4.py:contingency_metrics()`.

Текущий детектор полезен: сравнивает ответы после действия с фоном, использует prior и затухание. Но при конкурирующих действиях credit получает самое позднее, при равном времени приоритет выше у face, чем у gesture и call. Ответ на реплику может уйти последующему выражению лица. Признак «кто-то рядом» выводится из касаний, близости и движения; это не идентификация человека. Фон без действий может существенно отличаться от ситуации, в которой робот инициативен.

**Улучшить:** eligibility по типу и задержке, хранение уверенности и количества наблюдений; сопоставимые контрольные окна; сценарий yoked control с теми же ответами, но нарушенной зависимостью от собственных действий. Случайные поглаживания с другой частотой не полностью контролируют интенсивность стимуляции. Измерять воспроизведение конкретного успешного действия, а не только увеличение общего числа действий.

### A18 — P2: социальное восприятие ограничено интенсивностями

**Место:** `main/perception/vision_frontend.cpp`; `main/core/brain_loop.cpp`; `main/v4/channel_encoder.cpp`.

В v4 камера даёт движение/яркое пятно, а не надёжное распознавание человека, лица или объекта. Слух даёт акустические признаки и речь, но не понимание обращённости к роботу. Один усреднённый центр движения теряет несколько целей; отсутствие движения не означает отсутствия человека. Близость предмета не доказывает социальный контакт.

Это сознательное упрощение архитектуры, а не автоматически ошибка. Однако обещания «видит хозяина», «понимает игнорирование», «помнит, кому отвечать» должны ограничиваться реально доступными наблюдениями.

**Улучшить:** сначала оценка свежести и уверенности, затем один устойчивый объект внимания с временем последнего наблюдения. Распознавание человека добавлять только при измеримой пользе и допустимой стоимости. Для ощущения живости важнее удерживать внимание и слышать ответ, чем немедленно вводить семантическое понимание всего кадра.

### A19 — P2: независимость обучающей и проверочной выборок недостаточна

**Место:** `tools/v4/train_snn_v4.py:real_sequences(), train()`; `tools/v4/train_nn_v4.py:train(), fit()`.

Реальные фрагменты выбираются случайно из дневных потоков; соседние/пересекающиеся фрагменты могут попадать в разные части разбиения. У NN после первого fit DAgger выбирает данные из всего `pool`, включая исходные validation lives; затем новые rollout добавляются в training-часть. Отдельный `test` исключён из `pool`, но из-за пересечений исходных дневных фрагментов независимость по дням не обеспечена. Provenance окон не сохраняется.

**Исправить:** делить по дню/boot/сценарию до нарезки окон; запретить перекрытие, закрепить validation/test для всех DAgger-раундов; хранить происхождение и seed. Отдельно проверять редкие состояния и пределы hunger/tired, а не только среднюю точность копирования учителя.

### A20 — P2: PASS численного паритета не означает отсутствия локальных расхождений

**Место:** `tools/v4/parity_snn_v4.py`.

Критерий SNN — средняя ошибка <0,01. В аудите он прошёл, но максимальные расхождения составили 0,109 по `att_y` и 0,077 по `att_x` в отдельных последовательностях. Для спайковых динамических систем отдельные расхождения ожидаемы, но они могут влиять на пороговую реакцию. Нулевая округлённая средняя не означает битового равенства.

**Улучшить:** фиксировать хвост распределения, длительность отклонений и изменения решений/траекторий. Для монотонных потребностей добавить отдельные диапазонные проверки. Сверка реализаций доказывает переносимость вычислений, а не правильность психологического учителя или восприятия реального мира.

### A21 — P2: симулятор не покрывает важнейшие отказы настоящего устройства

**Место:** `simulator/build.sh`; `simulator/runtime/sim_runtime.cpp`; `main/robot_runtime.cpp`.

Общий BrainLoop — сильная сторона. Но симулятор не включает настоящий `RobotRuntime`, OTA/NVS/хранилище и его servo watchdog; время синхронизируется моделью штатно. Задачи выполняются на виртуальном RTOS по одной, поэтому обычный прогон не проверяет межъядерные гонки. Нет полноценной модели потери команд серв, питания и всех акустических особенностей корпуса. Заявление «цифровой двойник» стоит сопровождать границами модели.

**Добавить:** тестируемый отдельно safety supervisor; инъекции sensor stale/I²C timeout/потерь команд/рассогласованной позы/нет NTP/потерь дневника; host-тесты транзакций обновлений; ограниченные длительные прогоны и проверки переполнения миллисекундного счётчика.

### A22 — P2: воспроизводимость на чистой машине нарушена

**Место:** `README.md:Getting started`; `build.sh`; `firmware-builder/Dockerfile`, `firmware-builder/build.sh`; Git modes скриптов; `tools/requirements.txt`.

1. Dockerfile устанавливает системные инструменты и копирует bootstrap-скрипт, но сам не создаёт `/cache/esp-idf-v5.5.4`. `stackchan-v4/build.sh` сразу делает `source` этого пути. Успешная сборка в аудите использует существующий кэш; инструкция для чистого клона пропускает его подготовку. Старый bootstrap дополнительно обращается к `fetch_repos.py` официальной прошивки и не является готовой командой настройки v4.
2. `build.sh`, `flash.sh`, `simulator/build.sh`, `tools/v4/py` записаны в Git как `100644`. На текущем внешнем диске они выглядят исполняемыми, но после извлечения Git-версии на обычную ФС прямой запуск дал `Permission denied`. Сборка через `bash` сработала.
3. `data` — локальная игнорируемая ссылка на `../stackchan-life/data`; обучение зависит от местных дневников. `requirements.txt` содержит numpy/numba без фиксации версий; torch устанавливается отдельно. Скрипты сервисов предполагают конкретный путь `~/Codex/StackChan`.

**Исправить:** bootstrap v4, работающий с пустым кэшем; executable bits в Git; явные режимы «только запуск готовых весов» и «обучение с данными»; манифест окружения и моделей; создание каталогов и настройка путей. Проверять clean clone в CI. Большие дневники хранить отдельно с контролируемыми версиями/выборками.

### A23 — P2: HTTP-управление может надолго блокироваться одним запросом

**Место:** `main/net/ota_server.cpp:receive(), listenHandler()`.

При `HTTPD_SOCK_ERR_TIMEOUT` загрузка повторяет чтение бесконечно: общего дедлайна нет. Сервер обслуживается одной задачей, а `/listen` занимает её до 600 секунд. В это время status и операции обновления недоступны. Токен нужен и для этих запросов; риск остаётся при обрыве корректного клиента.

**Исправить:** общий дедлайн и предел последовательных таймаутов, отмена незавершённой записи, отдельный ограниченный поток/задача записи звука, доступность status во время stream. Проверять поведение клиента при busy и прерванной загрузке.

### A24 — P2/P3: документация местами описывает разные версии как одну текущую

**Места:** `docs/CREATIVITY.md`, `docs/HARDWARE.md`, `docs/DEVELOPMENT.md`, `docs/ARCHITECTURE.md`, `BRAIN_V4_PLAN.txt`.

Примеры: обучение readout Muse вместо реально изменяемого bias; «прогресс обучения» вместо ошибки прогноза; старые сведения о режиме отправки команд серв рядом с новыми; таблицы количества входов/колонок и числа сценариев; условное «действия согласованы по построению» при разной выдержке лица и параметров голоса. `NO_EMO_STRENGTH` существует в сети, но не используется текущим исполнителем лица. Не все заявленные выходы дают видимый эффект.

**Исправить:** в каждом концепте таблица «предложено / реализовано / измерено / опровергнуто / осталось». Текущие факты вынести отдельно от истории. Манифест размерностей генерировать из spec; требования к поведению хранить с версией и причиной изменения.

## 4. Идея живого робота: что оставить и что изменить

### Что уже правильно

- Работа без облака и без обязательной большой языковой модели соответствует задаче маленького автономного существа.
- Разделение быстрой оценки стимулов и более медленной политики понятно и позволяет искать причины поведения.
- Медленные состояния тела вынесены из спайковой сети в явные процессы; это делает их проверяемыми.
- Реальные дневники, отрицательные результаты в журнале, контрольные сценарии и паритет — важнее красивой биологической терминологии.
- Собственные инициативы, паузы, привычки, реакции на прикосновение и ограничения стимуляции подходят телу с двумя степенями свободы.

### Что сегодня означает «живой»

У системы есть вычислительные аналоги состояния, внимания и потребностей. Из этого нельзя заключить наличие субъективного переживания или сознания. Для проекта полезнее проверяемое определение: робот сохраняет контекст, проявляет инициативу по понятной причине, замечает ответ, адаптирует дальнейший выбор и остаётся узнаваемым через дни.

| Свойство | Состояние v4 | Следующая проверка |
|---|---|---|
| Реактивность | Работает в базовых сценариях | Реальные задержки и пропуски при движении/шуме |
| Инициатива | Muse, политика и взгляды исполнителя | Инициатива приводит к наблюдаемому ответу и корректирует следующий выбор |
| Телесные потребности | Есть давление сна и бюджет | Реальные отдых/расход изменяют активность независимо от нарисованного лица |
| Социальный обмен | Есть краткая контингентность | Услышанный ответ, повтор именно успешного действия, естественное ожидание |
| Личная история | Частично в learned blob; контекст сбрасывается | Вчерашний опыт меняет сегодняшний выбор после перезагрузки |
| Творчество | Структурированная вариативность заданного репертуара | Новая полезная комбинация сохраняется благодаря результату |
| Различение себя и мира | Эвристические маски | Измеренные false positives/false negatives в своих движениях и голосе |

Учителя задают врождённые предпочтения; это допустимый проектный выбор и прямо признано в плане v4. Но высокая точность копирования учителя не является доказательством развития собственного поведения. Эмоциональная голова ночью не обучается, поэтому изменение переживаемых категорий опытом сейчас особенно ограничено.

Социальная награда не должна означать «любой уход хозяина — плохо». Отсутствие внимания может быть нормальным. Нужны насыщение общением, ограничение повторных приглашений и спокойная самостоятельная активность. Иначе оптимизация внимания рискует закрепить назойливость. Это проектный риск, а не утверждение, что такое поведение уже возникло.

Модели Панксеппа, Барретт, Дамасио и исследования младенцев полезны как источники гипотез. Соответствие им нельзя устанавливать по одинаковым словам в именах переменных. Ближайший проверяемый ориентир — взаимная регуляция внимания, стимуляции и отдыха, как в [архитектуре Kismet](https://groups.csail.mit.edu/lbr/sociable/kismet.html) и её [системе потребностей](https://groups.csail.mit.edu/lbr/sociable/homeostatic-regulation.html).

### Архитектурное направление

Сохранить SNN и GRU как рабочую основу. Ввести общий контракт событий и исполнения, затем компактное устойчивое состояние тела/взаимодействия. Сеть выбирает намерение с длительностью и ожидаемым результатом; исполнитель возвращает факт и причину отказа; обучение использует этот же переход. Короткая память действий обслуживает текущий обмен, медленная память — устойчивые предпочтения. Лицо, голос и поза выражают согласованное состояние.

Возможные намерения: ориентироваться, наблюдать, пригласить к контакту, ответить, подождать, исследовать, отдохнуть. Это не требование заменить сеть новым огромным набором if/else: смысл намерений должен быть общим для обучения, прошивки, симулятора и журнала. Safety-ограничения остаются детерминированными.

Перед добавлением ещё одной сети сравнить текущую SNN с более простым baseline на одинаковых данных и бюджетах: качество реакции, задержка, память, устойчивость, энергопотребление. Сохранять SNN имеет смысл по её измеримой пользе и исследовательской цели, а не только по биологическому сходству.

## 6. Порядок улучшений

1. **Стабильность и сохранность.** Исправить A01–A07, валидировать транзакции обновлений, установить проверяемые ограничения отказов головы. Критерий: повреждённые данные отвергаются, неисправное обновление не подтверждается, ночная загрузка без сети тиха.
2. **Единая история опыта.** Ввести action_id, фактическое исполнение, валидность чувств, границы эпизодов, версии схем/моделей; исправить A08–A12. Критерий: одно и то же событие одинаково трактуется онлайн и ночью; нет награды на неизвестном будущем.
3. **Доказать пользу обучения.** Небольшой достижимый урок, например предпочтение одного из двух приглашений при одинаковом контексте. Сравнить до/после и контроль; проверить перенос на следующий день и откат. Факт изменения весов недостаточен. Подход AWR регрессирует взвешенные действия из опыта: [исходная работа Peng et al.](https://arxiv.org/abs/1910.00177).
4. **Живое взаимодействие.** Удержание внимания → пауза для ответа → распознавание ответа → повтор успешного действия → насыщение/выход из игры. Проверять в сопоставимых сценариях, где отличается только зависимость ответа от действия робота.
5. **Настоящий отдых и непрерывность.** Отделить сон от лица, сохранять медленные состояния и предпочтения. После насыщенного дня робот должен отдыхать по состоянию; после reboot сохранять смысл своей недавней истории.
6. **Развитие репертуара.** После предыдущих этапов — learning progress, выбор эксперимента, новые комбинации навыков. Для каждого нового механизма заранее определить наблюдаемую пользу, контрольный сценарий и способ отката.

Не требуется переписывать весь проект сразу. Наибольший эффект ожидается от согласования уже существующих подсистем и восстановления доверия к данным опыта.
